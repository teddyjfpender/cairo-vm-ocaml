# OxCairo PIE replay for Rust proving services

**Implementation contract • 28 November 2026**

Implement a synchronous, in-process call with an immutable snapshot. The caller submits a Cairo PIE archive and selects relocated trace, relocated memory, regenerated PIE, or any combination. A process-wide gate protects all pool-dependent work through the last byte of export. Returned bytes survive input disposal and subsequent executions. A single process can overlap proving and reading previous results with the next replay.

The sequencer can consume the regenerated PIE through its existing prover. Its privacy proof covers a separate bootloader execution. Replacing that execution requires a second witness interface and proof-level equivalence. This package defines the replay boundary, provides client code and records one positive and one negative differential experiment. The native v1 provider and the prover-witness extension remain implementation work.

## Integration with the 0.2 release branch

The release branch already provides [secure in-process replay](https://github.com/teddyjfpender/cairo-vm-ocaml/blob/71d5e92d7faa7eb27568fd53a328406fb442403c/bindings/c/oxcairo.h) with input and artifact **paths**. Its OCaml entry point, [Pie_run.replay_file](https://github.com/teddyjfpender/cairo-vm-ocaml/blob/71d5e92d7faa7eb27568fd53a328406fb442403c/src/runner/pie_run.ml), reads memory in chunks, wraps the run in `Felt.with_temporary_slots`, and joins artifact writers before returning. The C entry point starts the runtime on its first call and requires calls on the same OS thread. The proposed four new symbols add byte input, detached output views, explicit admission and profile-specific errors to that same shared library. Implement both entry points on the same runtime owner and exercise them together.

## Public contract

The normative declarations are in `include/oxcairo_pie.h` and `ocaml/oxcairo_pie.mli`. The safe wrapper and file-to-artifacts example are in `rust/`. The existing prover integration is a short source fragment in `rust/sequencer_integration.rs`.

* **Input.** One complete Cairo PIE ZIP in a counted byte span. Binary zeros are ordinary data. Version handling follows the pinned reader for supported archives, including its default for absent version.json. Support stored/deflated inputs and checked ZIP64 input lengths. Reject ambiguous duplicate required members with a format error, explicitly reporting an unsupported-input-policy difference if the pinned reader accepts them. Extract only recognized members in memory. The native parser must validate every offset, integer conversion, decompression length, CRC and segment sum before use, including bounds in C stubs and code built with `-unsafe`.
* **Profile.** ID 1 selects VM 3.2.0 secure PIE replay with the proving feature set including mod builtins. V1 layouts are `all_cairo` and `small`; a layout ID is separate from the profile. Start at the PIE main, use its declared steps, execution mode, trace collection on, secure=true, allow_missing_builtins=false, fill_holes=false, merge_extra_segments=false. Preserve finalized segment sizes. Trace collection remains on even for PIE-only callers. Select requested *exports* independently. No CLI fallback. Qualify each layout/profile before enabling it by default in a service. Unsupported IDs and unknown output bits fail explicitly.
* **Defaults.** OCaml default is the 3.2.0 profile, all_cairo, all three exports. Rust requires explicit exports. Default budgets are 1 GiB input, 4 GiB total inflated member bytes, 32 million steps, 64 million total logical segment cells and 4 GiB of output. These are proposed service defaults and adjustable per request; measured fixture sizes should guide deployment. Zero budgets, negative OCaml limits or an empty mask are argument errors. Duplicate OCaml/Rust output selections collapse into the mask. Enforce the segment cap both before initial growth and on subsequent VM growth, including sparse high offsets. All budgets apply in addition to platform, field and container representability limits; failure is atomic. Allocator slack, interpreter state, pool and GC are additional RSS.
* **Trace.** Contiguous little-endian tuples of three unsigned 64-bit words in AP, FP, PC order, one row per executed step in execution order, 24 bytes per row. Decode packed and full internal entries, including segment-qualified PC. Offsets use the finalized relocation table with first base 1. AP and FP are in execution segment 1. Use explicit little-endian writes; the inspected feat/os-pie C fast path copies native words. Treat the returned pointer as byte-aligned.
* **Memory.** Sparse records in increasing relocated address order, 40 bytes each. First 8 bytes are the unsigned absolute address, followed by a canonical nonnegative 32-byte felt, both little-endian. Relocatable values become their absolute addresses in the same table. Omit holes, preserve explicit zero cells. Reject unresolved temporaries or unrepresentable addresses. This buffer differs from the 40-byte records inside PIE memory.bin, which retain segment addressing and the value-type tag.
* **Revalidated PIE.** Success means validity checks, replay to end and pinned secure-compatibility checks completed, including when only trace is requested. Generate a fresh ZIP from the finalized runner if requested. Include version.json, metadata.json, memory.bin, additional_data.json and execution_resources.json. Pass output pages/attributes, Pedersen handling, main PC, stop pointers, ECDSA signatures and extra-segment sizes through the existing encoder. Recompute memory holes, do not copy the input's count. Secure replay derives Pedersen verification state from execution. The oracle compares steps and builtin counts; its input compatibility predicate omits holes and Pedersen data. Compare the *two regenerated outputs* including those fields in qualification.
* **Limits and ABI evolution.** Check compressed length immediately, cumulative claimed and actual inflated sizes before/during inflation, recorded steps against the limit before running, and output sizes with checked arithmetic before allocating. Budget total output across all requested buffers. For stored ZIP32 output, reject any unrepresentable member size, offset, central-directory size or start before truncation. Results are native addressable allocations, each at most PTRDIFF_MAX bytes. Initial target is 64-bit little-endian Linux. For v1 options, require `struct_size >= sizeof(ox_options_v1)`, read only the known prefix, keep semantics of defined bits fixed, reject unknown bits. New behavior that must be understood gets a new ID or major. Pin one provider image in the process. Bindings must tolerate unknown numeric status codes.

## Runtime and concurrent executions

1. **One admitted execution per address space.** Keep a process-wide try-gate covering parse, run, compatibility, snapshot encoding and cleanup. For a Rust host, bootstrap a dedicated native owner thread with once-only startup, initialize the embedded OCaml runtime there, register both replay callbacks once, and rendezvous synchronously with it. Route the existing path entry point through the same startup and admission mechanism; preserve its synchronous return convention and have it wait for admission. Keep the new snapshot call nonblocking on contention. Keep the runtime alive for process lifetime. A contending caller receives BUSY immediately and can use the host's bounded queue. No FFI callback enters Rust while holding the gate. Run blocking calls off Tokio reactor threads.
2. **Cross-language correctness.** Rust caller threads never touch the OCaml runtime. On the owner thread, use the runtime lock correctly around waits, CAML roots for live values and `caml_callback*_exn` with exception tests. Pass a request via a scoped custom block with bounded native copy/sink operations. Build all outputs under native RAII or a single C cleanup path. Publish only after the callback completes and pool cleanup succeeds. Translate anticipated parse/VM/mismatch errors at their origin; distinguish OCaml OOM from a deliberate limit. Catch all language exceptions inside the boundary. Native faults remain process failures. Disable unloading after first startup. For ordinary OCaml callers use the already-running runtime and the same admission/cleanup core; expose a separately linked host mode. A second runtime startup in an OCaml-hosted process is unsupported.
3. **Reuse the pool checkpoint.** `Felt.with_temporary_slots` saves the cursor and interning table, installs a fresh table and restores both with `Fun.protect`. Put parse, replay and every export within this scope; join all native writers before leaving it, including on failure. Audit signatures, access logs, cached hint closures and native scratch for retained run-local IDs. Exercise consecutive large-felt runs and error cleanup. If an internal failure leaves state uncertain, poison further admission until restart. Already detached bytes remain valid.
4. **Legacy entry points matter.** Keep the embedded core private to the single shared library providing the path and snapshot APIs. In an OCaml application using the same core, calling the legacy raw-runner API and retaining its pool-backed values across a reset is unsupported. To support mixing later, put a lease on *all* raw entry points for the lifetime of each live runner and any escaped felts, or move each runner to its own arena. A lock held only during raw execution cannot protect those values. No new public API exports them.
5. **Parallelism now.** One warm proving service process per active replay slot, each linked to the native library. Existing replicated service processes can own one slot apiece. A single coordinator can use long-lived worker executables with a bounded queue and shared memory/file descriptors for bulk bytes if it needs multiple slots. Start workers with exec/spawn before initializing their own runtime, never fork a live OCaml runtime to continue executing in the child. This introduces optional IPC; the one-slot in-process path has none. Keep permits and accounting for outstanding detached snapshots as well as active VMs. Waiting host requests can be cancelled; once admitted, cancellation detaches the waiter while the blocking task retains input until release. Hard deadlines or crash containment require process isolation.
6. **True in-process parallel replay is a separate change.** Thread an arena plus cursor and scratch through VM, decode and native kernels. Move builtin signatures/access logs and any re-entrant writer scratch into the run context. Audit shared opcode/hint state and static export buffers. Seal any read-only process-wide tables after initialization. Qualify interleaved runs on separate OCaml domains, GC pressure and repeated reclamation before lifting the gate. The v1 buffer ABI can remain stable.

## Implementation sequence

1. Give the existing deferred PIE reader a bounded in-memory source alongside its file source. Preserve chunked decoding and CRC checks, including on memory.bin. Refactor trace/memory relocation loops and PIE ZIP encoder to write to bounded sinks. Share the encoders with the CLI. Count rows and present cells, compute checked final sizes and fill native buffers directly where possible. Keep one immutable native allocation per artifact. For large PIE memory, stream into its final reserved span with incremental CRC; avoid constructing member strings, a growing ZIP buffer and a second detached output at the same time.
2. Implement the facade and shared gate around the existing pool checkpoint; keep entry points internal until parity gates pass. Fix the demonstrated ordering difference in the 3.2.0 profile. For sorted unique memory retain the current count fast path. For other input, preserve write-once insert/check semantics, compare the final address→value map to the reference, and count unique loaded addresses; never silently accept a conflicting duplicate by sorting it away. Verify duplicates with the pinned oracle. Leave the 4.0 comparison in a separate test lane and explicitly select compatibility mode where behavior differs.
3. Extend the existing Dune native shared-object target in [bindings/c](https://github.com/teddyjfpender/cairo-vm-ocaml/blob/71d5e92d7faa7eb27568fd53a328406fb442403c/bindings/c/dune). Keep `oxcairo_replay_v1` and add the four snapshot symbols to the same packaged `lib/oxcairo.so`. The reference Rust wrapper links the exact Linux filename; set its linker search path and the loader search path to the installation directory. Test a clean host in both call orders, path then snapshot and snapshot then path. Verify there is one runtime startup, serialized access and predictable cleanup after an error in either API.
4. Use a feature-gated adapter at a real serialized PIE ingress. Inside a blocking task request only PIE, parse the returned slice with pinned `CairoPie::from_bytes`, drop the native snapshot, and pass the owned Rust value into the existing `prove`. Preserve positive-count rejection for ecdsa, range_check96, add_mod and mul_mod. Existing callers that start with an owned `CairoPie` would need a writer over `Write + Seek` backed by a Cursor (factor the pinned `write_zip_file` implementation). Time that conversion explicitly. Avoid inserting a serialize/replay/deserialize cycle into ordinary proving unless that replay is required.
5. For a real **bootloader backend replacement**, introduce a Rust adapter over semantic bootloader witness data and make the old `adapt(&runner)` delegate to it. Inputs include segment lengths and holes, tagged relocatable memory and trace (PC segment/offset, AP/FP execution offsets), builtin segment IDs, public memory offsets/page positions, the bootloader context and its output preimage. Enforce address bounds before downcasts; preserve empty segments, builtin padding/order and public addresses. Feed this into the existing relocator, opcode classification and MemoryBuilder, compare complete ProverInput and output preimage, then prove and verify. Implement matching bootloader program/hints/proof-mode execution first. A consumer cannot recover all of this from the two flat replay buffers. Keep the replay ABI independently usable.

## What can consume the reported speedup?

Issue #35 reports four large and one virtual-OS fixture against Rust 4.0.0. The reported 4.7–5.1× concerns large-PIE execution. Its example is 6.27 s Rust versus 1.24 s OxCairo for 14.6 million steps. The branch CLI records input load, replay and total separately; writing the requested artifacts occurs after the replay timer. The reported roughly 9 GB versus 3 GB peak is a fixture observation under the issue's configuration. The timings are arithmetic inputs here, not a measured VM 3.2.0 or Rust-service speedup.

Compare equivalent work at the same ingress and egress. Let R and O be execution times, H_R and H_O include conversions, queue wait, export, adaptation and any other stages inside the chosen boundary. The measured service ratio would be (R + H_R)/(O + H_O). To beat Rust the condition is H_O − H_R < R − O. If OxCairo is an added preflight before an unchanged prover, **no Rust replay time has been removed**; the applicable baseline is the original prover, plus any validation it already performs.
